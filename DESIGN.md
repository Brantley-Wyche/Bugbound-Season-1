# Design System: Bugbound Season 1

## Overview

**Creative North Star: "The on-call field notebook"**

Bugbound uses dark graphite, warm offwhite, and subdued amber to make debugging feel like working through a practical notebook. Ruled registers, prominent folio numbers, and a continuous lesson document give the interface its identity.

The shell is restrained and readable beside an editor. Typography, alignment, and thin rules establish hierarchy; decorative cards and colored side-border sections are outside the approved direction. A prominent amber setup notice explains the desktop requirement while keeping lesson browsing available. This document records the implemented system in `src/styles/global.css` and `src/shell/`; it is a design reference, not a review report.

**Key Characteristics:**

- Dark graphite surfaces with warm offwhite reading text.
- Subdued amber for primary actions, open incidents, and folio numbers.
- Thin rules and aligned entries instead of a card grid.
- Public Sans prose paired with compact monospaced references.
- Native navigation and optional disclosure within a continuous document.
- A prominent desktop setup notice that preserves lesson browsing.
- Saved completion distinguished from the most recent verification run.

## Colors

The palette pairs slightly green graphite neutrals with paper-like text and a restrained amber accent. The frontmatter records the shell's active color primitives; the stylesheet remains the implementation source. Sidecar tonal ramps are synthesized preview metadata, not additional application tokens.

### Primary

- **Subdued amber — accent:** primary actions, current incident numbers, open status, disclosure markers, selection, keyboard focus, and the full desktop setup notice surface.

### Neutral

- **Dark graphite — bg:** the page canvas and text on filled primary actions.
- **Soft graphite — bg-soft:** the live preview stage, inline code ground, and linked register-row hover.
- **Graphite panel — panel:** disabled shell buttons; also inherited by exercise demos.
- **Ruled graphite — border:** register rows and document section dividers.
- **Strong graphite rule — border-strong:** register headings, preview outline, and outlined buttons.
- **Warm offwhite — text:** primary reading text, headings, and the primary button's hover surface.
- **Muted sage grey — muted:** concepts, metadata, explanatory notes, quiet controls, and locked status.

Feedback uses **sage — ok** for resolved incidents and passing checks, **soft coral — err** for failed checks and preview crashes, and **pale blue — info** for code references. These are functional signals rather than a second brand palette.

**The Status Text Rule.** Color reinforces explicit words such as Open, Locked, Resolved, Completion saved, PASS, FAIL, and PEND; it does not carry the state alone.

## Typography

**Display and body font:** locally hosted Public Sans, with Segoe UI and system sans-serif fallbacks. The variable font loads with `font-display: swap`.

**Reference font:** Cascadia Mono, Consolas, and platform monospace fallbacks.

The sans serif stays direct and readable. Monospace is reserved for reference numbers, compact status text, progress counts, paths, and check errors. The large folio is light Public Sans, not monospace.

### Hierarchy

- **Display:** the register introduction uses the frontmatter display role; the mobile override is `clamp(38px, 10vw, 52px)`.
- **Headline:** lesson titles use the headline role, reducing to (30px) on small screens.
- **Title:** section headings use the title role, with observed context-specific sizes in the register, assignment, and resolution.
- **Body:** the body role establishes the base. Concept prose opens to a line height of (1.85) and a maximum measure of (70ch).
- **Label:** compact mono references use the label role; most descriptive metadata instead uses sans serif at (12px).
- **Folio:** lesson numbers are (62px), weight (250), line height (1), and tabular numerals; mobile reduces them to (44px). The larger assignment number follows the same light, tabular treatment.

The frontmatter includes descriptive contextual and responsive roles for every font-size value used in the shell, including the notice, assignment count, hints, verification, footer, and relative inline code. Sidecar typography metadata identifies the corresponding contexts. Responsive roles apply only at their documented breakpoint.

**The Reference Type Rule.** Keep prose in Public Sans and reserve monospace for operational references and measured results.

## Layout

The application has a centered maximum width of (1200px), with desktop horizontal padding of (48px). A ruled header and footer frame the content without a sidebar or sticky shell.

The register introduction uses two columns. Incident rows align a number, title, concept, and right-aligned text status on continuous horizontal rules. The current incident gains stronger title weight and amber numbering rather than a surrounding card.

The lesson is one document. Above (900px), the report, concept disclosure, and hints occupy the left column while preview and verification occupy the right; the ratio is (1 : 1.1), with a normal column gap of (64px). At or below (900px), sections follow their DOM order in one column: report, concept, preview and checks, then hints.

At or below (1050px), column gaps tighten to (36px) and the long season descriptor disappears. At or below (900px), page padding becomes (32px). At or below (600px), padding becomes (20px), the introduction stacks, incident concepts move below their titles, section navigation becomes two columns, and progress moves to its own header row. The prominent desktop setup notice has its own visibility condition: at or below (1100px), or on a device matching both `hover: none` and `pointer: coarse`, including wider touch-first tablets. It sits below the header and above either page. At (600px) and below, its icon stacks over the text and its padding reduces from (24px) to (20px). It does not block browsing.

Spacing is built from recurring compact, row, group, and section intervals rather than a rigid universal grid. Preserve the existing content order and reading measure when extending the shell.

## Elevation & Depth

The shell has no box shadows. Thin rules separate the continuous document; a slightly lighter surface and stronger outline distinguish the live preview. Primary buttons use a flat fill. Hover changes color or border without a lift or scale effect.

**The Continuous Document Rule.** Use rules and spacing to separate lesson sections; reserve the outlined inset surface for the live preview rather than wrapping every section in a card.

## Shapes

The register and document remain square and open. Small radii soften actual controls and the preview enclosure: use the frontmatter control and stage radii. Inline code uses the modest code radius recorded in the frontmatter. Avoid introducing pill containers or colored side-border cards into the shell.

The book-outline brand mark is an inline SVG with an open notebook spine and short ruled strokes. Folio numbers and horizontal rules carry the notebook identity through the remaining interface.

## Components

### Buttons

Primary amber buttons carry starting, continuing, and verifying actions; outlined secondary buttons support recovery. Both use the frontmatter button padding and control radius with a minimum height of (44px). Primary hover changes to warm offwhite; outlined hover brightens its border. Disabled buttons use the panel surface, muted text, a subdued border, and the waiting cursor.

Quiet actions such as Restart preview use underlined muted text with a minimum height of (44px). Reset progress uses the related underlined control but changes to the error color on hover.

Interactive elements use a (2px) amber focus outline offset by (4px); linked register rows bring that outline inside with an offset of (-2px). Color, background, and border transitions last (150ms). Reduced-motion preference removes those transitions.

### Navigation

The linked wordmark returns to the register. The lesson back link remains a native anchor. Section jumps use native buttons with generous vertical hit areas, muted text at rest, and amber underlined text on hover. A section jump scrolls to and focuses its target without changing the hash route; the concept target also opens its native disclosure.

A skip link appears on focus. Route changes focus the page title. Do not replace these interactions with visual-only click targets.

Section jumps use native buttons that scroll and focus the target without changing the hash route. Incident-to-incident navigation remains links.

### Incident register

Rows are ruled list entries, with a minimum height of (64px). Available entries are links; locked entries remain visible non-interactive rows. Resolved and open entries have explicit status labels. Hover only applies to linked rows. Mobile keeps the number and status aligned while placing the concept under the title.

### Concept and hint disclosures

The concept is a native `details` element, closed initially. Its summary has a minimum height of (56px), a native amber marker, and a muted topic beneath its main label. Opening it reveals continuous prose between thin horizontal rules.

Hints use full-width buttons with a minimum height of (52px), an explicit tier label, `aria-expanded`, and an associated hidden panel. They begin concealed. Their appearance remains part of the document, with no side-border card.

### Desktop setup notice

A full amber surface with dark graphite text and the shared stage radius carries the desktop requirement. The heading is followed by the local editor, Vite recompilation, and desktop-browser workflow, then a semibold reassurance that lessons remain browsable. The inline monitor SVG is (32px). It is a labelled aside rather than an overlay or disabled-state screen. Preserve the source visibility condition described in Layout.

### Live preview and verification

The preview is the one outlined inset stage, using the frontmatter preview surface, radius, and padding; mobile padding is (16px). Its boundary contains a titled, borderless iframe with the intentionally broken exercise and any caught crash. The quiet Restart preview button is connected by `aria-describedby` to the note beneath the stage: restarting reloads the exercise, clearing component state and timers while source files and progress stay intact.

Verification is a ruled log beneath the preview. Each row aligns a compact textual status with its check name. Error messages use wrapping monospaced text. Passing, failing, and pending are separate readable states; the results region announces updates politely. A semibold Last run summary reports the passed count after a run finishes; the accompanying note states that results describe that run and must be refreshed after source edits. The live region remains present when empty.

### Saved completion and continuation

The saved-completion summary uses a sage heading, muted explanatory copy, a thin bottom rule, and the existing primary continuation link. Its language is historical: Resolution recorded and Completion saved. It invites checking the current source without promising restored result history. An empty log on a completed visit explicitly says no checks have run in this visit. Saved completion is not a claim that current source passes.

When a completion write fails, the metadata says Completed this visit and the summary explicitly says progress has not been saved. A storage notice above the main content uses the existing error-colored full outline, (20px) padding, and a native retry button. The notice announces its message through status semantics. Retry saving progress and Retry reset identify the failed operation accurately. Reset confirmation occurs before the initial reset; retrying an already-confirmed failure does not ask again.

An additional native text continuation link sits beside the verification workflow, below its results and last-run note, whenever completion is saved and checks are not running. Saved completion and the last-run results can coexist even when a later check fails. The saved-completion announcement uses a persistent polite, atomic live region.

### Progress

The header shows fifteen small rectangular segments with an adjacent resolved count. Completed segments use sage and remaining ones use the rule color. The accessible progressbar exposes numeric progress. On mobile, the segments become short horizontal marks.

### Exercise-local controls

The shell has no general-purpose input, tag, or card primitive. The `lv-` controls belong to the educational previews and retain their own examples and styling. Their fields, tags, themed panels, and charts are not templates for new shell surfaces.

## Do's and Don'ts

### Do:

- **Do** preserve the ruled incident register and continuous lesson document.
- **Do** use amber for primary actions, open status, folios, and visible keyboard focus.
- **Do** pair status colors with readable state labels.
- **Do** keep native links, native concept disclosure, and explicit hint controls.
- **Do** retain readable wrapping and the single-column lesson order on narrow screens.
- **Do** implement the shell with simple React and plain CSS.
- **Do** make the desktop setup requirement prominent while allowing lesson browsing.
- **Do** distinguish saved completion from last-run verification and keep continuation beside the log.

### Don't:

- **Don't** reintroduce a generic card grid or colored side-border lesson cards.
- **Don't** turn exercise-local cards, inputs, tags, or chart styles into shell primitives.
- **Don't** add shadows, decorative motion, Tailwind, or an SCSS system to reproduce this design.
- **Don't** expose hidden hint content as decoration or sample copy.
